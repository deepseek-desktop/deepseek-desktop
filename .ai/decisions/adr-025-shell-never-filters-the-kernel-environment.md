# ADR-025：壳不过滤内核环境

## 状态

已采用。修订 `.ai/architecture.md` 第 3 条与 `.ai/conventions.md` 中「不通过长期环境变量传递 API Key」的表述，两者原文把「桌面不提供明文凭据」写成了「Harness 不接收任何环境变量」。扩展 [ADR-012](adr-012-harness-repository-system-proxy.md) 的同类判断。

## 背景

桌面用一张 24 项的白名单构造 Harness sidecar 的环境，其余一律丢弃。白名单里没有任何代理变量，而内核的 `@deepseek-ai/dsh-http-proxy` 的设计正是「launcher 读一次标准代理环境变量，普通 fetch 调用方无需改动」。结果是内核的代理支持永远拿不到策略，LLM、联网搜索和网页获取一律直连；在需要代理的网络下表现为连接失败，或被 SSRF 护栏拦下的污染 DNS 解析。用户观察到的是网页获取死循环。

这不是孤例，是一种复发模式：ADR-012 记录过同一形状的问题，只是低一层（Finder 启动不继承代理变量导致仓库 `ls-remote` 超时）。白名单的失败方式尤其糟糕——它**静默**丢弃，内核侧没有任何信号，只能从表象倒推。内核可以从环境读取的东西不止代理：CA 证书、locale、包管理器配置，以及官方搜索插件明确声明的启动环境凭据回退。

## 决策

- Harness sidecar 继承桌面进程的**完整环境**，不做任何过滤。白名单删除，不以任何谓词替代——不引入denylist，也不做凭据名匹配。
- 桌面自己拥有的名字在继承之后写入，因此仍然覆盖同名项。
- 回归断言的是「不存在过滤」本身：对照实时进程环境逐项比对，任何谓词被重新引入都会在此失败，而不是在用户机器上静默关掉某个内核功能。

## 理由与边界

被删掉的那条约束原本是为了不让长期明文凭据进入 Harness 环境。核对后它与桌面的实际安全模型不是一回事：桌面保管的凭据存在加密保险库里，经受限 helper 会话交给内核，这条通道没有改变。而用户自己 `export` 的变量本来就在桌面进程的环境中，把它传给桌面启动的子进程不产生新的存储、不写日志、不扩大暴露面——那是操作系统的默认行为，白名单才是那个例外。

代价是明确的：用户在 shell 里 `export DEEPSEEK_API_KEY` 后，该值会直达 Harness 进程，绕过桌面保险库。这恰恰是内核官方搜索插件声明的回退路径（`launchEnvironmentOf(ctx).get(apiKeyEnv)`），过滤它同样属于壳阻断内核功能。用户明确要求壳不得限制内核，本决策按该要求执行。

未纳入本决策的两处壳侧约束，理由不同，保持不变：

- bundle 补丁停用官方 `credentials` 插件，是用桌面加密保险库**替换**它，不是阻断；放开会同时存在两套凭据系统并废掉保险库。
- 工作台 WebView 不获得通用 Tauri Shell、文件系统或 IPC capability，防的是网页内容而非内核进程；放开等于拆掉浏览器沙箱。

本决策不改变任何内核默认值，也不对签名、公证或真实供应商验收作出声明。
